一、结论

报错不在网关，也不在密钥：DSH 的 opencode-go-deepseek provider 直连 https://opencode.ai/zen/go/v1，不经本机 OmniRoute。 Connection error. 是 OpenAI SDK 的 APIConnectionError——即 fetch 本身抛错（本例 TypeError: fetch failed … cause=ETIMEDOUT，约 260ms 即失败）。

二、机理

Node fetchundici + keep-alive
→
DNS 双栈A 172.65.90.23
AAAA ×4（无路由）
→
Happy Eyeballs250ms 预算内
IPv4 未完成即被放弃
→
回落 IPv6本 WSL 无 IPv6 默认路由
尝试即刻失败
→
ETIMEDOUT≈260ms 抛出
→「Connection error.」
为何时好时坏：连接时延在 250ms 上下抖动（实测 0.250–0.389s），故仅部分请求越界失败； 失败后 DSH 退避重试（用户所见「重试延迟 4120 毫秒」，多为 4.1s 后成功），呈现「偶发中止」。 空闲后 undici 复用连接需重新建连，因此长空闲再发车时命中率最高。

五、边界、残留与后续

  • 进程级生效：该 flag 覆盖 DSH 全部出网 provider（opencode.ai、openrouter 等）；对走 127.0.0.1 的 omniroute-rust 无影响。
  • 不适用：opencode-web.service 是 ELF 单体二进制（非 Node CLI 入口），该 flag 不生效。
  • 根因仍在网络侧：到 Cloudflare 边缘 272–390ms 不在本机可控范围；若日后时延继续增大，把预算提到 3000–5000ms 即可。
  • 重启副作用（与本次无关）：journal 显示插件 dsh-better-sidebar@0.21.1 与 dsh 0.2.0-rc.1 不兼容被跳过——如侧栏消失属此因，与本次修复无关。
  • 排障顺序（可复用）：先判 provider 是「直连上游」还是「走本机网关」→ 再看是否是 SDK 包装层错误（Connection error. 属传输层）→ 最后用 NODE_OPTIONS 矩阵 + time_connect 对表。
