一、结论先行

两个报错同源，且都不是「密钥/配置写错」。根因是组合回退链在单个候选失败后被静默截断： record_failure() 写入的是 provider 级冷却，而 is_available() 按 provider 判定， 于是同一 provider 的其余全部候选在冷却窗口（鉴权/配额/限流 120s）内被跳过。 当组合的目标恰好扎堆在这一个 provider 上时：
表象真实机制
coding-plan 502 … attempts: 0 唯一候选 qwen 配额耗尽（429）→ 写 provider 冷却 → 同 provider 三个候选全被跳过 → 一次上游都没发，返回无原因的裸 502。
coding-flash 「API 密钥无效」 首跳 opencode-go 抖动失败 → 同 provider 三个候选被跳过 → 落到唯一存活目标 dev-one-blog（余额不足）；末态状态码取自「最后一个候选的错误」，一旦尾候选是 401，DSH 即渲染成 message.failure.auth = API 密钥无效。

佐证：DSH 文案映射实测于 @deepseek-ai/dsh-client-ui-chat/lib/client.js 的 message.failure.auth；网关侧 sk-or-ef31… 密钥有效（同一个键请求 coding-free 一直 200）。

七、遗留风险与建议

  • 同 provider 扎堆仍是结构性风险：候选排序应尽量跨 provider 交错；建议前端/运维在组合编辑时给出「同一 provider 占比」提示。
  • 半开探测的频率：每个软跳过 provider 每请求最多 +1 次上游尝试（受 MAX_GLOBAL_ATTEMPTS=30 约束）。对已确认长期失效的 provider，建议直接从组合摘除而非依赖探测。
  • 配额类失败仍走 provider 级冷却：qwen/dev-one-blog 属账号级，保留 provider 级语义合理；若出现「单模型配额」型上游，可再按 provider|model 细分冷却。
  • 部署中断提醒：本机网关即本会话 LLM 通路，重启期间 DSH 工具调用曾报 transport 错误；后续在此环境重启建议 systemctl --user restart --no-block，或安排在会话收尾时执行。
