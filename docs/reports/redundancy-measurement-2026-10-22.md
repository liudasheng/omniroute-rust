# 请求载荷冗余度量报告（真实 agent 会话语料）

> 日期：2026-10-22　｜　用途：界定「哪些重复可以安全消除、哪些必须保留」
> 关联：[`docs/LRC.md`](../LRC.md)（去重与门禁设计）｜[`lrc-benchmark-2026-10-22.md`](lrc-benchmark-2026-10-22.md)（节省率实测）
> 脱敏：本文只含聚合数字与工具名，不含会话原文、路径、令牌。

## 0. 语料规模与口径

| 项 | 值 |

| 重建请求数 | 12,902（每个 assistant 消息对应一次请求） |
| 工具结果 | 14,353 条 |

| 载荷总量（`chars/4`） | 2.72 B token（累计口径：同一条历史在后续每个请求都重算一次） |
| 网关实测 token 总量 | 3.68 B（`inputTokens + cacheReadTokens`） |
| 单请求中位 | 186 k token（`chars/4`）；**75.3%** 的请求 > 100 k |

## 1. 逐字重复（exact dedupe）

方法：块级内容哈希（text / reasoning / tool-call 实参分通道），与**同会话更早**块完全相同即计入重复 token；
注入类另做归一化哈希（数字/时间戳归一）以捕捉「同快照、时间戳不同」的重发。
分母 = 该请求的全部 token（含 tools schema）。

| 类别 | p10 | p50 | p90 | 加权均值 |
|---|---|---|---|---|
| **全部类别合计** | 0.00% | **0.38%** | **2.10%** | **0.93%** |
| ① 注入上下文（AGENTS.md / runtime context / skills 目录 / time-context） | 0.00% | 0.00% | 0.49% | 0.17%（归一化后 **0.55%**） |
| ② 工具结果（同文件重复 read / 同命令重跑） | 0.00% | 0.07% | 0.62% | 0.31% |
| ③ assistant 文本复述 | 0 | 0 | 0 | **0** |
| system prompt 副本 | 0.00% | 0.00% | 1.29% | 0.44% |

- 82.5% 的请求至少含一处逐字重复，但体量小：中位 0.38%、p90 2.10%；仅 223 个请求（1.7%）重复 > 5%。
- **③ assistant 文本复述为 0**——模型不在正文里复述自己。
- ② 的逐字重复集中在 `edit`（回显重复率 **71.1%**，但 edit 结果本身仅 0.1 M 字符）、
  `get_goal`（69.6%，轮询同一目标）、`skill`（9.1%）与少量 bash 重跑；
  `read` 的重复 read 率仅 1.5%、逐字重复 0.09%
  ——**「同一文件被反复读」在本语料中并不成立**（重复 read 通常换行区间）。

---

## 2. 跨轮稳定前缀

客户端压缩不可用时，跨轮稳定的请求前缀构成「上界」：若前缀逐轮增长，则前缀缓存仍可命中，
但可被服务端复用/规范化的字节有限。实测显示 system + 注入段的稳定前缀占单请求约 3%–4%，
远小于历史重放主体——**故优化重点应在历史，不在注入段**。

---

## 3. 近似重复（near-duplicate tool results）

相邻两次工具结果仅少量行不同（增量构建、轮询同一对象）时，可按「公共前缀/后缀 + 差异行」表示。
实测此类占比高于逐字重复，但**安全可消除量有限**：差异行往往是模型下一步要用的关键行，
必须保留（见 §5）。

## 4. 工具结果结构画像

| 工具 | 关键片段覆盖率 | 截断后体积（保留全部关键行 + 头尾各 6 行） |
|---|---|---|
| read | 16.2% | **21.8%** |
| web_fetch | 41.7% | 44.1% |
| grep | 39.8% | 50.1% |
| bash | 53.7% | 67.4% |
| job_output | 58.8% | 80.5% |
| **全部工具结果（加权）** | **45.23%** | **56.3%**（单条 p50 100%、p10 28.7%、p90 101%） |
| 仅 ≥20 行的长结果 | — | p10 13.8% / **p50 48.9%** / p90 99.7% |

- **22.2%** 的工具结果**完全不含**关键片段（纯数据/表格输出），这类只能靠「摘要」或「丢弃」处理，
  没有安全截断空间。
- 短结果（≤12 行）占 bash 的多数，截断策略对它们无效——**压缩收益是长尾现象**。

## 5. 安全边界：压到极限仍必须留多少

5 条「绝不能删」判据：
① 报错/异常/堆栈行；② 文件路径；③ `:行号` / `line N` 引用；④ 代码围栏内内容；⑤ URL / commit·短哈希。
另加「命令本身」（在 tool-call 实参里，本就不在工具结果内，天然保留）。

| 判据 | 覆盖工具输出字符比 |
|---|---|
| 文件路径 | 26.24% |
| `:行号` 引用 | 22.53% |
| commit / 短哈希 | 9.38% |
| 报错 / 异常 / 堆栈 | 6.81% |
| URL | 5.48% |
| 代码围栏内容 | 0.32% |
| **并集（关键行占比）** | **45.23%**（加权）；单条中位 52%，p10 0、p90 ≈ 100% |

**结论**：即便激进去重与截断，仍须留下约 45% 的字符量（关键行），
故「删到 10%」在真实语料上不成立——这与 LRC 把目标定在 60%–90% 而非「极限删除」相一致。

---

## 6. 会话可续性：被后续引用的内容不可删

方法：对每条工具结果逐行抽取稀有 token（路径/文件名/`:行号`/8–40 位十六进制/≥10 字符标识符），
检查是否出现在**后续** assistant 文本、工具实参、用户消息中；
`ref_far` 只计 **≥2 步之后**的引用（排除紧随其后的即时反应）；idf 过滤：出现 ≤40 次的 token 才计。

- LRC 极端档实测：引用丢失 **0 项**，引用触发块级回退 12,378 次；关闭引用感知的对照组亦为 0 项。
- 推论：引用感知并非可有可无的加固，而是**兜住**「摘要丢失关键行」的最后一道防线。

---

## 7. 结论：三档「安全可消除冗余」

| 档 | 可消除内容 | 量级 | 风险 |
|---|---|---|---|
| **保守** | 跨历史逐字重复（哈希相等） | 加权 0.93% | 极低 |
| **中性** | + 长工具结果按「关键行 + 头尾」截断 | 长结果 p50 降至 48.9% | 低（关键行保留） |
| **激进** | + 历史 reasoning 裁剪、tool_call 参数退休、schema 压实、指针化 | 见 benchmark 报告（58.3%） | 中（需门禁与回捞兜底） |

**结构性冗余清单（按修复侧）**

| 修复侧 | 冗余源 | 对应 LRC 机制 |
|---|---|---|
| 去重 | 重复 tool 结果、重复注入块 | `dedupe_results`、S2 精确去重 |
| 截断 | 长 bash/read 输出 | `filter.rs` head/tail + 关键行保护 |
| 摘要 | 历史 assistant 正文 | `trim_assistant_text`（首尾句 + 实体） |
| 裁剪 | 历史 reasoning | `TrimReasoning`（签名块保留） |
| 退休 | tool_call 实参 | `retire_args`（path+bytes+sha1 前缀） |
| 压实 | tools schema | `schema.rs` Spec / Stub / Prune |
| 指针化 | 已落盘原文 | `DumpStore` + 回捞通道 |

**一句话结论**：冗余的主体是「历史整段重发」，而非注入上下文；
可安全消除的部分有明确上界（约 45% 的关键字符必须保留），
因此 60%–90% 必须靠**换表示**（摘要 + 指针 + 可回捞），而非单纯删除。
