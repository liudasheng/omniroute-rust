# LRC 实测报告：真实 agent 语料上的节省率、门禁通过率与保真度

> 日期：2026-10-22　｜　对象：`src/compression/lrc/`（LRC 分层可逆压缩）与既有六档压缩
> 设计稿：[`docs/LRC.md`](../LRC.md)　｜　策略总纲：[`compression-strategy-2026-10-22.md`](compression-strategy-2026-10-22.md)
> 语料来源：agent 会话日志（压缩为 zstd 的逐轮 JSONL），**仅取统计量，不含任何原始会话全文**

---

## 0. 结论速览

1. **既有六档省得不够**：最好一档中位节省 34.0%、加权 33.2%，且**改动消息中 19.9%–72.1% 发生保真破坏**
   （lite 70.2%、aggressive 72.1%、standard 58.2%、rtk 33.1%、ultra 19.9%）。
   「破坏」= 被改动的消息里丢了报错行 / 文件路径 / 代码围栏 / diff hunk / URL 之一。
2. **瓶颈不在规则强度，在作用面**：真实请求中 90.4% 的 token 来自 3 步以前的历史；
   历史 reasoning 26.4%、历史 tool_call 参数 21.4%、bash 结果 20.2%、tools schema 9.6%
   —— 这四块既有引擎**全部碰不到或只能破坏性删**。
3. **LRC 实测**：保守 13.3% / 中性 48.4% / 激进 58.3% / 极端 68.6%（加权），
   **门禁通过率 100.0%、保护片段还原率 100.00%**（极端档 schema 整块剪除的理论上限为 71.9%）。
4. **口径**：token 一律用 `ceil(utf16_code_units/4)`（与网关估算器一致），并以每步 provider usage
   校准（中位系数 1.26×）。报告同时给出「估计口径」与「真实口径」两列。
5. **缓存会计**：prompt cache 命中率全语料 80.1%–86.6%（视 provider）。
   缓存命中的部分省的是**钱**，不省**配额**——「省 token」必须先声明按哪个口径汇报。

## 1. 语料与口径

| 项 | 值 |
|---|---|
| 语料规模 | 100 会话 / 13,683 步 / 818 轮 / 30,885 条消息（zstd 逐轮日志） |
| 载荷总量 | M1（`ceil(utf16/4)`）3.03B token；真实（provider usage）3.78B token |
| M1 低估程度 | 真实 ≈ M1 × 1.30（p50，tiktoken 校准） |
| 单步载荷（M1，含 reasoning 重放） | 中位 191.0k · p90 426.1k |
| 单步载荷（真实） | 中位 246.7k · p90 542.2k |
| LRC 原型语料 | 30 会话 / 1,372 请求快照 / 基线 prompt 214,664,401 token / 耗时 423.5s |

**口径约定**

- M1 = `ceil(utf16/4)`，与 `src/compression/estimate.rs` 一致；
- 真实 = provider `usage.inputTokens + usage.cacheReadTokens`（每步校准后求比值，中位 1.26×）；
- 「一个请求」= 某条 assistant 消息之前实际发送的 messages 快照
  （system + 注入段 + 历史 assistant/reasoning/args + 工具结果 + tools schema）。

## 3. 既有六档压缩的真实收益与保真破坏

### 3.1 节省率（586 步真实载荷，100 会话语料）

| 档 | 节省率 p50 | p90 | 语料加权 | 改动步占比 | 归零步占比 |
|---|---|---|---|---|---|
| aggressive | 34.0% | 49.3% | 33.2% | 100.0% | 0.7% |
| lite | 34.6% | 50.8% | 33.8% | 98.8% | 0.4% |
| ultra | 23.4% | 41.2% | 26.5% | 100.0% | 5.2% |
| rtk | 23.0% | 40.0% | 24.8% | 98.8% | 9.0% |
| standard(caveman) | 18.2% | 36.3% | 21.7% | 99.8% | 12.4% |

### 3.2 联合判据：节省率 × 保真破坏

| 档 | p50 节省 | 加权节省 | 改动消息中破坏率 |
|---|---|---|---|
| aggressive | 42.2% | 47.2% | **72.1%** |
| lite | 41.2% | 46.0% | **70.2%** |
| standard | 20.9% | 27.3% | 58.2% |
| rtk | 27.3% | 31.2% | 33.1% |
| ultra | 24.8% | 31.3% | 19.9% |

> 两表口径不同（3.1 为 100 会话全语料、3.2 为 586 步受控子集），故绝对值有差，
> 但**同一口径内的相对排序一致**：aggressive/lite 破坏最重、ultra 最轻。

**结论**：既有档不是省不下来，而是**省的方式会毁会话**——这正是要换打法的原因。

### 3.3 作用面矩阵（构造性事实）

| 字段 | lite | standard | aggressive | ultra | rtk | LRC |
|---|---|---|---|---|---|---|
| `messages[].content`（string） | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `content` parts 数组的 text | 部分 | ✅ | ❌ | ✅ | ❌ | ✅ |
| `tool_calls[].function.arguments` | ❌ | ❌ | ❌ | ❌ | ❌ | ✅（退休） |
| 历史 reasoning / thinking | ❌ | ❌ | ❌ | 部分（破坏性） | ❌ | ✅（裁剪 + 签名块保留） |
| `tools` JSON schema | ❌ | ❌ | ❌ | ❌ | ❌ | ✅（Spec/Stub/Prune） |
| Claude `tool_result` 块 / 顶层 `system` | ❌ | ❌ | ❌ | ❌ | ❌ | 部分 |
| 保护片段还原率 | 无保障 | 无保障 | 无保障 | 无保障 | 部分 | **100%** |

两处真缺陷（已在 LRC 侧规避）：
`aggressive` 的降级链把 `system` 硬编码进 `compress_roles`（绕过 `preserve_system_prompt`）；
`ultra` 不保护末条 user（直接剪当前指令）。

## 4. LRC 各档实测

### 4.1 组合档位

| 档位 | 加权 | 真实口径 | 中位 | p10 | p90 | 闸门通过率 | 保护还原 |
|---|---|---|---|---|---|---|---|
| 保守档 S0+S1+S2+S4轻 | **13.3%** | 13.4% | 14.7% | 7.8% | 25.7% | 100.0% | 100.00% |
| 中性档 +S3 B 摘要 | **48.4%** | 48.9% | 48.9% | 34.2% | 57.1% | 100.0% | 100.00% |
| 激进档 +S3 C 指针 | **58.3%** | 58.6% | 58.3% | 41.5% | 65.7% | 100.0% | 100.00% |
| 极端档 +纯指针/推理删除/stub schema | **68.6%** | 68.8% | 68.2% | 54.3% | 75.2% | 100.0% | 100.00% |
| 极端档+ · schema 整块剪除（理论上限） | **71.9%** | 72.4% | 73.4% | 60.1% | 80.4% | 100.0% | 100.00% |

**一句话**：在门禁全通过前提下，可行上限为 **68.6%**（极端档）；**71.9%** 为剪除 schema 整块的理论上限；
「90%」需要牺牲的是**保护内容的在场上文**（P1 报错行与 P2 身份片段只能以 digest 寻址）、
**推理链整块丢弃**与**未用工具 schema 的语义完整性**。

| S2 · 跨历史精确去重 | 812/1372 | 0.3% | 0.0% | 0.6% | 0.2% |

### 4.3 tools schema 三档（未用工具剪枝）

「未用」= 该步之前会话历史中从未出现过的工具名。三档对同一「保留集合」做结构校验：

| 子测 | schema token 前→后 | 节省率 | 保留工具 | 剪掉/降级 | name 不变 | required 不变 | 参数名不变 | schema 合法 |
|---|---|---|---|---|---|---|---|---|
| ① Spec（仅 S1） | 605,682 → 280,082 | 53.8% | 2240 | 0 | ✅ | ✅ | ✅ | ✅ |
| ② Stub（name+单行描述+扁平参数名） | 605,682 → 166,775 | 72.5% | 198 | 2042 | ✅ | ✅ | ✅ | ✅ |
| ③ Prune（整块删＝理论上限） | 605,682 → 20,517 | 96.6% | 198 | 2042 | ✅ | ✅ | ✅ | ✅ |

> Prune 的「保留集合不变」只对**被保留的工具**成立——被剪掉者模型无法再调用，故为理论上限而非可行方案。
> Stub 保留 name / required / 参数名与类型，仅丢描述与嵌套结构。

### 4.5 引用感知与回捞成本

- 引用丢失：极端档 **0 项**；关闭引用感知的对照组亦为 0 项。
- 引用触发块级回退：12,378 次。
- 回捞成本：被删块中 **18,401 / 412,267（4.5%）** 在后续步骤被 read 或重跑命令再次拉取
  ——这部分删除要付二次 IO，是压缩收益的净扣减项。
- 极端档中 reasoning 贡献 26,761,434 token，占总节省 18.2%（推理链整块删除）。

## 5. 复现方法

LRC 原型可在本仓库直接复跑：

```bash
# 单次压缩诊断：逐块归因「为何被压 / 为何未被压」
cargo run --bin lrc_diag -- <messages.json>

# 全量测试（门禁与保真断言内置其中）
cargo test
```

语料侧的统计脚本（生成 §2–§4 表格）为一次性分析工具，不随仓库分发；
其口径与断言已在 `src/compression/lrc/` 的单元/集成测试中固化。

## 6. 限制与敏感信息

- 本报告只引用**脱敏后的统计量与短片段**，不含原始会话全文、密钥、路径或凭据。
- 语料含多 workspace 会话；统计量与具体项目名解耦，报告中不列 workspace 清单。
- `chars/4` 对中文密集内容偏差可达 2–3 倍（R² 为负），跨语种结论不可直接外推。
- 「节省率」为**请求 prompt token** 口径，不等于账单降幅：缓存命中部分省的是钱而非配额。
